## Goal

**`TransportTapIntent` is a shallow module — its interface is wider than its implementation, and it
has exactly one caller.** The whole implementation is one expression:

```swift
// Models/TransportTapIntent.swift:10-12
static func play(for state: TransportLaunchState) -> Bool { state == .stopped }
```

wrapped in an enum, a static func and an 8-line doc comment. The sole production caller is
`Views/TransportButton.swift:180` — `onTap(TransportTapIntent.play(for: state))`.

Apply the **deletion test**: inline `state == .stopped` at the call site and complexity does **not**
reappear across N callers — there is exactly one, and it already holds the state. The module was
extracted purely to give the one-liner a unit test (`Tests/TransportTapIntentTests.swift`, 3 cases).
That is a hypothetical seam, not a real one.

Consider inlining the rule and keeping the intent as a comment at the call site.

## Acceptance Criteria

- [ ] Decision made and recorded: inline `TransportTapIntent`, or consciously keep it (see the
      counter-argument below) — either is acceptable, but the shallowness should be a choice, not an
      accident
- [ ] If inlined: `TransportTapIntent.swift` and `TransportTapIntentTests.swift` are removed, the
      rule lives at `TransportButton.swift:180` with a comment naming the intent, and the build +
      remaining suite stay green
- [ ] If kept: a one-line note on why the module stays (e.g. the test is load-bearing
      documentation) so a future review doesn't re-raise it

## Notes

**This is the lowest-confidence item in the review (Speculative), and deliberately so.** The
counter-argument is real: the test documents "a tap while stopped plays; otherwise it stops," a
transport rule this app cares about getting right, and un-extracting trades a test for a comment.
It's worth doing only if `play: state == .stopped` reads as obviously correct at the call site.

This is the *inverse* of T-020/T-021/T-022 — not all extraction is deepening. A pure function pulled
out for a unit test, with one caller and an interface larger than its body, is shallow by
definition; naming that is the point of the review, even when the verdict is "leave it."

No firmware/protocol risk here — `state == .stopped` is app-side transport intent, and the quantized
arm/fire behaviour is unaffected (this only decides which *request* a tap sends).

Source: architecture review 2026-07-14 (candidate 05).
