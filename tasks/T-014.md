## Goal

**The app cannot see a real device.** Verified on hardware 2026-07-14: a KitchenSync Touch on the
LAN advertises as `kstouch-dfd0`. `KitchenSyncDiscovery` filters:

```swift
names.filter { $0 == "kitchensync" || $0.hasPrefix("kitchensync-") }
```

`kstouch-dfd0` does not match. The device is **invisible** — not shown wrong, not shown offline.
Absent.

This is the prefix heuristic failing exactly as its own doc comment predicted, on the first real
device the app was ever pointed at.

## Acceptance Criteria

- [ ] A real KitchenSync Touch (`kstouch-*`) appears in the device list
- [ ] When a TXT record is present, match on `dev` — never on the hostname
- [ ] When TXT is ABSENT, fall back to hostname matching (`kitchensync-*` AND `kstouch-*`)
- [ ] A host named `kitchensync-whatever` that is NOT one of ours is rejected once TXT is available
- [ ] The matching rule is a pure function with tests — no `NWBrowser` in the test loop
- [ ] Written test-first per the /tdd rule
- [ ] Verified against real hardware, not a stub

## Notes

**The fallback is not optional.** Firmware in the field has no TXT record and won't until it is
reflashed (`link-devices` ESP-031). Matching on TXT *only* would make every existing device
disappear — a worse bug than the one being fixed. So: TXT when present, hostname prefix otherwise,
and widen the prefix set to include `kstouch-`.

The prefix fallback stays a heuristic and should be labelled as one in the code. It exists to keep
un-updated units working, not because it is correct.

`NWBrowser` surfaces TXT via the result's `metadata` (`.bonjour(NWTXTRecord)`). Extract the decision
so it is testable without standing up Bonjour:

```swift
enum DeviceMatch {
    static func isKitchenSync(serviceName: String, txt: [String: String]?) -> Bool
}
```

The `NWBrowser` glue stays dumb; the rule gets the tests.

The TXT half depends on `link-devices` **ESP-031**. The hostname-fallback half depends on nothing
and should land NOW — it is what makes the Touch visible today.
