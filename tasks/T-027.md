## Why (the SoftAP flow's worst step, removed)

[T-026](T-026.md) provisions a new device over its SoftAP: the user leaves their network,
joins the device's open AP (no internet — iOS nags), types their SSID + password, then must
**remember to switch back** before Bonjour can rediscover the now-joined device. That WiFi
juggle is the fiddliest, most-abandoned step in onboarding.

**BLE provisioning removes it entirely.** The phone stays on its normal WiFi the whole time;
credentials travel over a separate radio. The device can **scan and return the nearby SSIDs**,
so the user picks from a list instead of typing. And it's more secure — the SoftAP posts the
WiFi password over an unencrypted local link; BLE provisioning is encrypted with a
proof-of-possession. This is the HomeKit/AirPods-class first-run experience.

Keep T-026 as the **baseline + fallback** — it needs zero firmware change and covers any device
or moment where BLE isn't available. Most IoT products ship BLE-primary *with* a SoftAP
fallback. This ticket is the premium path layered on top, not a replacement.

## Firmware dependency (gating)

- BLE provisioning is an **ESP-IDF** capability (`wifi_provisioning` + `scheme_ble`). It lands
  naturally **with the ESP-026 convergence** (the Touch moving off Arduino to ESP-IDF), not
  before — track the firmware half there or in its own `ESP-*` ticket when scheduled.
- **Native on the S3** (Touch / Super Mini have BLE 5). The **P4 is harder**: its WiFi/BLE come
  through the C6 co-processor, so provisioning there is more involved — scope the S3 first.
- Costs RAM (BLE+WiFi coexistence) and flash; fine on the S3. Needs a proof-of-possession /
  QR-code security scheme decided with the firmware.

## App side

- Use Espressif's **`ESPProvision`** Swift SDK (SPM/CocoaPods) or CoreBluetooth by hand against
  the ESP provisioning protocol (`prov-session` → `prov-scan` → `prov-config`).
- Requires the **Bluetooth entitlement** + `NSBluetoothAlwaysUsageDescription` in the Info.plist
  (mirror how T-011 added the Local Network keys via `project.yml`).
- Reuse T-026's transport-agnostic guts: the device is still confirmed and shown the same way;
  only the *credential transport* changes (BLE vs `POST /save`). Factor the setup flow so the
  view model takes a provisioning transport, not a hard-coded HTTP call.

## Acceptance criteria

- [ ] From a factory-fresh device, the app provisions WiFi over BLE **without the phone ever
      leaving its own network**.
- [ ] The device scans and the app shows nearby SSIDs; the user picks one and enters a password.
- [ ] Provisioning is encrypted (PoP), not plaintext.
- [ ] SoftAP (T-026) remains the automatic fallback when BLE isn't available.
- [ ] Firmware BLE provisioning is scoped to the S3 first; the P4 (C6) is a follow-on.

## Notes

Gated on ESP-026 (ESP-IDF convergence) for the firmware half — do not start the firmware work
