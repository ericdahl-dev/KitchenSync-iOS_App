## Goal

`KsConfig.outputCount = 4` is baked in, but the fleet is not uniform: **KitchenSync Touch is the
one-MIDI-output version.** A device with one clock output must render one card, not one real card
and three dead ones.

The device already tells us how many it has — `/status.launch[]` and `/config.json`'s `clock[]` are
arrays. Read their length instead of asserting a constant.

## Acceptance Criteria

- [ ] `DeviceDetailView` renders one `OutputCardView` per element of `config.clock`, whatever the
      length
- [ ] `KsStatus.launch` of length 1 decodes and drives transport correctly
- [ ] `transportSummary` works over a `launch` array of any length
- [ ] Nothing indexes `launch[i]` or `clock[i]` without checking `indices.contains(i)` — a
      length mismatch between `/status` and `/config.json` must not crash
- [ ] `KsConfig.outputCount` is either removed or demoted to a MAXIMUM, never an assumption
- [ ] Written test-first per the /tdd rule, with 1-output and 4-output fixtures
- [ ] Verified against a real 1-output Touch

## Notes

`saveFormFields` currently emits `clk0_*` … `clk3_*` by iterating `clock.enumerated()`, so it
already follows the array — good. The constant is used for **WiFi slots** too
(`KsConfig.wifiSlotCount`), which is a genuinely different thing and stays fixed at 3. Don't
conflate them.

Watch `LiveRebootPartitionTests`: it builds the live-key set by iterating `0..<KsConfig.outputCount`.
If that constant changes meaning, the partition test's coverage silently narrows. Keep it iterating
a MAXIMUM so the test still covers every key the firmware could accept.

The firmware side must emit honest lengths rather than padding a Touch's `launch[]` to four — see
`link-devices` **ESP-029**. If it pads, this task cannot tell a real output from a filler one and
the dead-cards bug comes back.
