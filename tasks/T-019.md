## Goal

**A live device can look unreachable because `.local` resolution flaked, not because the device
went anywhere.** Observed on real hardware, 2026-07-14, mid-session:

```
curl http://192.168.0.101/status        -> HTTP 200      (the device, answering fine)
curl http://kstouch-dfd0.local/status   -> timeout
dns-sd -B _http._tcp local              -> kstouch-dfd0  (STILL ADVERTISING)
```

Bonjour **browse** worked. Bonjour **resolution** didn't. The device never moved.

The app builds every request URL from `<name>.local` (`KitchenSyncDevice.host`), so when that
happens the app reports the device UNREACHABLE (T-010's three-strike counter) even though it is
sitting there answering on its IP.

## The trade this re-opens

`KitchenSyncDiscovery`'s doc comment makes a deliberate choice, and it's a good one:

> *"Deliberately does NOT resolve the matched service to a raw IP via NWConnection… Instead this
> hands the hostname straight back as `<name>.local`, and URLSession resolves that through the
> system's mDNS responder exactly the way Safari resolves it… one resolution path, not two."*

The reasoning holds — one resolution path is easier to debug than two. **But we have now seen that
path fail on a device that was fine**, so the cost of the trade is no longer hypothetical.

## Acceptance Criteria

- [ ] Discovery captures the resolved IP alongside the hostname (an `NWBrowser` result can be
      resolved via `NWConnection`, or via the `.service` endpoint's resolution)
- [ ] `.local` stays the PRIMARY path — it is the one Safari uses and the one users can type
- [ ] On repeated `.local` failures, retry against the last known IP before declaring UNREACHABLE
- [ ] A device that has genuinely gone away is still reported UNREACHABLE (T-010 preserved — do not
      trade one false signal for another)
- [ ] The IP is treated as a CACHE, not as truth: DHCP moves, and a stale IP that now belongs to
      someone else's box must not be talked to. Re-resolve on success; discard on mismatch.
- [ ] Written test-first per the /tdd rule

## Notes

**Be careful what this fixes.** T-016 already established that a device answering in a dialect we
can't read is `.unsupported`, not `.unreachable`. This adds a third case: a device that is *there*
but whose NAME won't resolve. Three distinct failures, three distinct signals — do not collapse
them, which is the mistake this codebase keeps making (see T-009, T-010, T-016, T-018).

**A stale IP is a real hazard, not a theoretical one.** DHCP hands addresses around; if we cache
192.168.0.101 and the Touch later moves, that address may belong to a laptop. Talking to it is at
best useless and at worst confusing. Trust the name; use the IP only as a fallback, and only until
the name works again.

Consider whether this is worth doing at all before ESP-031 lands (TXT records) — the same
`NWConnection` resolution that yields the IP is where TXT gets read, so the two touch the same code.
