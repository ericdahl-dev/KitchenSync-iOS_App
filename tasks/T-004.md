## Goal

The one missing view model. `DeviceListViewModel` handles the fleet (discovery, manual hosts, a
2s `/status` fan-out); this handles a single device once you've drilled into it: poll its status,
fetch its config, and dispatch edits down the two write paths.

## Acceptance Criteria

- [ ] `@MainActor` `ObservableObject`, one `KitchenSyncClient` for one host
- [ ] Polls `GET /status` while the detail view is on screen; cancels when it isn't
- [ ] Fetches `GET /config.json` on appear (404 case is T-009)
- [ ] Live edits dispatch via `postLive(_:)` with a `KsLiveEdit` — never an ad-hoc field string
- [ ] Full saves dispatch via `postSave(_:wifiEdits:)` and surface the reboot (T-007)
- [ ] Transport taps dispatch via `postTransport(output:play:)`
- [ ] Written test-first per the /tdd rule, against a stubbed `URLSession` — no device needed

## Notes

**The two write paths are not interchangeable, and the type system already enforces it.**
`/live` is a partial patch applied immediately, restricted to `KsLiveEdit`'s closed case set.
`/save` is the full form: it persists to NVS and *reboots the device*. Anything absent from
`KsLiveEdit` — WiFi credentials, the `metronome` and `follow_beat` enable flags — is reboot-only,
because the ES8311 codec and I2S only come up at boot. Route those through T-007's settings
sheet, never through a live slider.

Consider a faster poll here than the list's 2s, since this is where transport arming is watched
(T-003). Whatever the interval, cancel on disappear, and guard re-entry the way
`DeviceListViewModel.start()` does (`guard pollTask == nil`) — SwiftUI's `.task{}` re-invokes on
every re-appear.
