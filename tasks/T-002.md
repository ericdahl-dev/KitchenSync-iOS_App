## Goal

Execute the five existing test files for the first time. They have never been run — they were
traced by hand against the `link-devices` firmware source, because the container that wrote
them had no `swift test`. A hand-traced test is not a passing test.

Treat every one of them as unverified until the runner says otherwise.

## Acceptance Criteria

- [x] `KitchenSyncAppTests` runs in Xcode / `xcodebuild test`
- [x] All five files pass: `TransportTapIntentTests`, `FormURLEncodingTests`, `KsLiveEditTests`,
      `KsStatusDecodingTests`, `KsConfigTests`
- [x] Any failure is diagnosed against the *firmware source*, not patched to match the Swift —
      if the two disagree, the firmware is right and the Swift is the bug (moot: no failures)
- [x] A green run is recorded in this task's Progress section

## Notes

The fixtures were built from the firmware's actual `snprintf` / `ks_config_set()` output rather
than plausible-looking JSON, so a failure here more likely means the Swift misread the protocol
than that the fixture is wrong. Check against:

- `KitchenSync/main/ks_config.c` — `ks_config_set()`, the form grammar
- `KitchenSync/main/ks_config_json.c` — `/config.json` output, `#%06X` colors
- `KitchenSync/main/ks_web.cpp` — the route handlers

`TransportTapIntentTests` is the one file written genuinely test-first, so it's the most likely
to pass unchanged. The other four were backfilled — they're the ones to be suspicious of.

### One build-config fix was needed first

The test target failed to code-sign: *"the target does not have an Info.plist file and one is
not being generated automatically."* The test bundle had never been configured with one, because
it had never been built. Fixed in `project.yml` — NOT in a plist file, per the T-001 lesson
that XcodeGen regenerates those — by setting `GENERATE_INFOPLIST_FILE: YES` on the
`KitchenSyncAppTests` target. Also pinned `SWIFT_VERSION` and `SWIFT_STRICT_CONCURRENCY` on the
test target to match the app target, so tests are compiled under the same rules as the code they
cover.

### What this does and doesn't establish

It establishes that the *pure logic* is right: encoding, decoding, state mapping. It establishes
nothing about the network layer or discovery, neither of which has a test or has ever spoken to
a real device. `KitchenSyncClient` and `KitchenSyncDiscovery` remain unexercised — the first real
proof will be T-005 pointed at actual hardware.
