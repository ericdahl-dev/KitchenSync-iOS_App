## Goal

**Getting a box onto WiFi currently requires the user to leave their own WiFi.**

Today: the device fails to associate → falls back to a SoftAP called `KitchenSync-Setup` at
192.168.4.1 → the user **disconnects from their own network**, joins the device's AP, fills in a web
form, and rejoins. Per box.

At home that's annoying. At a venue, onto house WiFi, with three units on the bench and a soundcheck
running, it's miserable — and it's precisely the moment you can't afford to drop off the network
you're working on.

BLE provisioning removes the detour entirely: the app talks to the device over BLE, hands it
credentials, the device joins WiFi. **The phone never leaves its network.**

The app is the right place for this. It already owns the device list, so "add a device" and "get a
device onto WiFi" should be the same flow, not two unrelated rituals in two different apps.

## Acceptance Criteria

- [ ] The app discovers un-provisioned devices over BLE
- [ ] The user picks a network and enters a password **without leaving their WiFi**
- [ ] Proof-of-possession is sent — an unauthenticated box must not accept credentials
- [ ] After provisioning, the device appears in the normal Bonjour device list
- [ ] The failure path is honest: wrong password, out of range, device already provisioned
- [ ] `NSBluetoothAlwaysUsageDescription` is in `project.yml`'s `info.properties`
      (**not** in Info.plist — XcodeGen regenerates that; see CLAUDE.md)
- [ ] Written test-first per the /tdd rule — the protocol/state logic is testable even though
      CoreBluetooth itself isn't

## Notes

**Blocked on `link-devices` ESP-033**, which must ship the device side first — and which starts with
a feasibility spike, because the **ESP32-P4 has no native radio**. WiFi *and* BLE both run through
the onboard C6 over `esp_hosted`, and BLE must not destabilise the WiFi stack that Ableton Link
depends on. If that spike fails, this is S3/Touch-only, or dead.

**Do not remove the SoftAP path.** A phone with BLE off, or a laptop, still needs a way in. This is
an additional door, not a replacement.

Espressif ships an iOS provisioning library that speaks their `wifi_provisioning` protocol —
evaluate it before hand-rolling CoreBluetooth. Hand-rolling a security-relevant protocol is not
where this project should spend its risk budget.

### BLE is for provisioning ONLY

Recorded so nobody relitigates it:

- **Never for clock or MIDI.** BLE MIDI jitter runs into the tens of milliseconds. This product
  exists to be *tight* — ESP-027 was a crisis because the DIN clock went silent for 138 seconds, and
  ESP-028 exists to prove pulses are actually on the wire. A clock over BLE is hostile to the whole
  point of the product.
- **Probably not for discovery.** Tempting, since this app's own empty state says *"Some guest
  networks block discovery."* But BLE only helps you FIND a device; you still need IP connectivity to
  do anything with it, and a network blocking mDNS usually blocks client-to-client traffic too. You'd
  find a device you still can't talk to.

Full reasoning in `link-devices` **ESP-033**.
