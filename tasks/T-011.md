## Goal

Make KitchenSync units identifiable on the LAN, instead of guessed at.

**This task's fix lives in the `link-devices` repo, not this one.** It's filed here because
this is the repo that suffers from it, and because a heuristic nobody wrote down is a heuristic
nobody fixes.

## Acceptance Criteria

- [ ] Firmware advertises a distinguishing TXT record (or a service subtype) alongside
      `_http._tcp` — `mdns_service_add()` in `KitchenSync/main/wifi_link.c`
- [ ] `KitchenSyncDiscovery` matches on that record instead of the hostname prefix
- [ ] A non-KitchenSync host named `kitchensync-whatever` is no longer picked up
- [ ] Ideally the TXT record also carries the chip target, which would let T-008 refuse a
      cross-target firmware flash

## Notes

Today the firmware advertises **generic** `_http._tcp` with no TXT record and no subtype
(ESP-012). So `KitchenSyncDiscovery` browses *every* `_http._tcp` responder on the network and
keeps the ones whose Bonjour service name is `kitchensync` or starts with `kitchensync-`. That
works only because passing a null instance name to `mdns_service_add` makes ESP-IDF default the
instance name to the hostname.

It is a heuristic, and it has a real false-positive: any host that happens to be named
`kitchensync-*` gets adopted into the fleet. On a private LAN that's unlikely; at a venue with
someone else's gear on the network, less so.

Written up in `link-devices`: `docs/plans/2026-07-14-ios-kitchensync-app-plan.md`.

Low priority because the current heuristic works in practice and the fix requires a firmware
release plus a re-flash of every unit — but it's the kind of thing that gets forgotten and then
costs an afternoon at a show.
