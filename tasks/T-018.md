## Goal

**The diagnostics warning dot is permanently lit on a healthy device.** Found on real hardware,
2026-07-14.

`DeviceDetailView.hasDiagWarning` is:

```swift
return t.droppedTicks > 0 || t.overruns > 0
```

But **these are LIFETIME counters** — the firmware says so explicitly (`ks_tick_health.h`:
*"Lifetime counters, not windowed — a worst-case that scrolled past is not a measurement."*).

So the real `kstouch-dfd0` reports `drop:47`, accumulated **once at boot**, and the dot is amber
**forever**. Sampled every 4s for 32s: `drop` never moved off 47, `over` stayed 0. The clock is
perfectly healthy and the app says otherwise, permanently.

**That is alarm fatigue by construction.** A warning that is always on is a warning nobody reads,
and it will be ignored on the one day it means something.

## The actual distinction

| | means | what a user should do |
|---|---|---|
| `drop` non-zero but **static** | the device dropped ticks at some point (boot, WiFi association) and is fine now | nothing |
| `drop` **increasing** between polls | the clock task is dropping ticks RIGHT NOW | this is the fault ESP-027 was about — investigate |

The app polls `/status` continuously, so it can see the delta. It just isn't looking.

## Acceptance Criteria

- [ ] The warning fires on an INCREASE between polls, not on a lifetime total being non-zero
- [ ] A device with `drop:47` static shows **no** warning
- [ ] A device whose `drop` climbs between polls **does** warn
- [ ] The counters are still DISPLAYED (they're real data — just not alarming)
- [ ] Distinguish visually: "47 dropped since boot" reads differently from "dropping now"
- [ ] Survives a device reboot, where lifetime counters reset to 0 — a decrease must not be
      mistaken for a fault, or read as a huge negative rate
- [ ] Written test-first per the /tdd rule, with fixtures for static / rising / reset-after-reboot

## Notes

**This is the same error, a fourth time.** Today already: a `/config.json` 404 is not a dead network
(T-009); a decode failure is not an unreachable device (T-016); one dropped poll is not a
disconnection (T-010). Now: a lifetime counter is not a live fault. Every one of them is the same
shape — **two different situations collapsed into one signal, and the user sent to fix the wrong
thing.**

Worth generalising the rule rather than fixing it a fifth time: *before showing a warning, ask what
the user would DO about it. If two causes need different actions, they need different signals.*

`maxStepMicros` is deliberately still un-warned — nobody has told us a threshold, and inventing one
would be worse than showing the raw number. That decision stands and is unaffected by this task.

Bench evidence (kstouch-dfd0, current firmware, 2026-07-14):

```
t+ 4s  drop=47  over=0  gap=1487  work=229  pulses=8550
t+32s  drop=47  over=0  gap=1487  work=229  pulses=8550    ← identical, 8 samples
```
