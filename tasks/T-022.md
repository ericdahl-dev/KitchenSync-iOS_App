## Goal

**There are two state→face mappings for the transport, and only one of them is tested.** The
per-output button correctly routes through the pure, tested `TransportAppearance.appearance(for:
linkOwned:)` (`Models/TransportAppearance.swift:29-44`, consumed at `Views/TransportButton.swift:25-27`).
The **master** transport re-derives the same kind of decision inline in the View:

- `Views/DeviceDetailView.swift:243-249` — `playFace` maps `TransportSummary → TransportFace` by hand
- `Views/DeviceDetailView.swift:230` — `blinks: vm.status?.transportSummary == .arming` inline
- `Views/DeviceDetailView.swift:213-220` — `summaryText` maps `TransportSummary → String`

This is a decision (state → appearance) living in a `View`, which the codebase's own rule says
belongs on a model as a pure function — and it is a decision **on stage**, with no test behind it,
running parallel to a tested one it can silently diverge from.

Deepen: extend `TransportAppearance` (or add a sibling constructor) to cover the master-summary
case, so both the per-output button and the master button cross one interface.

## Acceptance Criteria

- [ ] The master transport's face + blink decision is produced by `TransportAppearance` (or a
      sibling pure function), not by `playFace` / inline expressions in the View
- [ ] That mapping is tested directly, the way `TransportAppearanceTests` tests the per-output case
- [ ] The two-buttons-not-one-toggle design is preserved (`DeviceDetailView.swift:222-241` — a single
      derived toggle shows the wrong thing during a mixed arming/playing moment; keep PLAY and STOP
      separate)
- [ ] Armed still blinks at beat rate; no soft `repeatForever` throb (armed is a cocked hammer)
- [ ] `summaryText` stringification either moves onto the model alongside the face, or is left as
      pure presentation — pick one home, don't leave the decision half in the View
- [ ] Written test-first per the /tdd rule

## Notes

Scope check: `TransportButton`'s `TransportFace → Color` switches (`:112-149`) are pure presentation
and should **stay** in the View — `TransportAppearance`'s own doc says "turning a face into a
gradient is not [worth testing]." This task is only about the *state → face/blink* decision, which
is the part that belongs on the model.

Watch the transport-is-quantized rule: the master face must be derived from the device-reported
`transportSummary`, never predicted client-side. No local timers for the arming→running flip.

Source: architecture review 2026-07-14 (candidate 03). Lower leverage than T-020/T-021 but a clean,
contained win — one tested mapping instead of two, one of them blind.
