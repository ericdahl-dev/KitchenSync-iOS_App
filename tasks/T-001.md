## Goal

Get the Phase 1 scaffold to compile for the first time. Nothing in this repo has ever been
through a Swift compiler — it was written in a headless container with no toolchain. There is
also no `@main` App type and no root view, so even a clean compile wouldn't launch.

This blocks every other task. Do it first, on a real Mac.

## Acceptance Criteria

- [x] `brew install xcodegen && xcodegen generate` produces `KitchenSyncApp.xcodeproj`
- [x] `KitchenSyncApp.swift` exists with an `@main` `App` and a root view (a placeholder list
      is fine — the real `DeviceListView` is T-005)
- [x] The `KitchenSyncApp` target builds with zero errors
- [x] The app launches in the simulator without crashing
- [x] `SWIFT_STRICT_CONCURRENCY: complete` is still on and the build is warning-clean under it

## Notes

Expect real work here, not a formality. Likely suspects:

- **Strict concurrency.** `project.yml` sets `SWIFT_STRICT_CONCURRENCY: complete`.
  `DeviceListViewModel` is `@MainActor` but hands a closure to `KitchenSyncDiscovery`, which
  fires it on its own `DispatchQueue`. `KitchenSyncClient` is a `struct` captured into a
  `TaskGroup`. Both are plausible Sendable diagnostics.
- **`KsStatus` decoding** — confirm the `launch[4]` array and the `Decodable` conformance line
  up with what the firmware actually emits.
- **`String(format:)`** in `KsConfig`/`KsLiveEdit` on the `UInt32` overloads.

## Progress

Done — Xcode 26.6, Swift 6.3.3, xcodegen 2.45.4.

**The scaffold compiled clean on the first real build.** Zero Swift errors, zero warnings, even
under `SWIFT_STRICT_CONCURRENCY: complete` (verified applied via `-showBuildSettings`). None of
the three predicted failure modes above materialised — the Sendable diagnostics in particular
never appeared. The only build failure was the expected missing `_main`.

Added `Sources/KitchenSyncApp/KitchenSyncApp.swift`: `@main` + a deliberately inert `RootView`
placeholder (a `ContentUnavailableView`). It is meant to be deleted by T-005, not grown.

### Two Info.plist defects found by actually launching it

Both would have been invisible from reading the Swift, and one of them was fatal:

1. **`NSLocalNetworkUsageDescription` + `NSBonjourServices` were missing.** Since iOS 14 both are
   required to browse Bonjour or reach a `.local` host. Without them `NWBrowser` returns no
   results *and* `URLSession` cannot resolve the device — silently, with no useful error. The
   entire discovery path was dead on arrival. `NSBonjourServices` is set to `_http._tcp`, which
   is what `KitchenSyncDiscovery` browses (see T-011).
2. **`UILaunchScreen` was missing**, so iOS ran the app letterboxed in legacy compatibility mode
   at a reduced screen size. An empty dict is the modern opt-in.

### The trap worth remembering

**XcodeGen *generates* `Sources/KitchenSyncApp/Info.plist` from `project.yml` on every run.**
The first fix went into the plist directly and was silently overwritten by the next
`xcodegen generate`. Plist keys must be added under `info.properties` in `project.yml` — there
is now a comment there saying so. The generated plist is still committed, but it is an artifact:
`project.yml` is the source of truth.

Also switched `CFBundleShortVersionString`/`CFBundleVersion` to `$(MARKETING_VERSION)` /
`$(CURRENT_PROJECT_VERSION)`; they were hardcoded to `1.0`/`1` and disagreed with `project.yml`.

Not done here: the test suite has still never been executed — that is T-002.

Do NOT hand-edit the generated `.xcodeproj` — it's gitignored. `project.yml` is the source of
truth; if a build setting needs changing, change it there and regenerate.
