## Goal

The per-output MIDI clock start/stop control — the most recently requested feature, and the
reason the transport model layer already exists. `TransportLaunchState` and `TransportTapIntent`
are both written and tested; this is the view that drives them.

`TransportButton` renders one output's launch state and dispatches a tap. `OutputCardView`
wraps it with that output's config summary (cable, ppqn, phase, swing).

## Acceptance Criteria

- [ ] `TransportButton` renders all three `TransportLaunchState` cases distinctly:
      `.stopped` = dark, `.armed` = blinking, `.running` = solid
- [ ] A tap calls `postTransport(output:play:)` with `play: TransportTapIntent.play(for: state)`
      — do not re-derive the intent inline
- [ ] The button reads state from the polled `/status.launch[N]` and does NOT keep a local
      optimistic "armed" state
- [ ] `OutputCardView` shows the output's config and embeds the button
- [ ] Written test-first per the /tdd rule — the tap logic is already covered, so the new tests
      here cover the state→appearance mapping

## Notes

**Play is quantized; Stop is immediate.** A tap on `.stopped` arms the output, which waits for
the next bar line before it runs. That asymmetry is Ableton's own launch behaviour and it is
deliberate. The blinking `.armed` state is therefore load-bearing UI, not decoration — it is the
only feedback that the tap registered, and it may persist for most of a bar.

Do not add a client-side timer to guess when `.armed` flips to `.running`. The device computes
and reports it on every poll. If the 2s list poll makes the flip render late, the fix is a
faster poll on the detail screen (T-004), not a local guess.
