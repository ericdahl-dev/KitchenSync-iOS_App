## Goal

Push a firmware `.bin` to a device over the air. `KitchenSyncClient.uploadFirmware(_:)` already
does the transport — raw body, no multipart, straight into the inactive OTA slot (P4-017,
dual-slot). This is the file picker, the progress UI, and the guardrails.

## Acceptance Criteria

- [ ] File picker limited to `.bin`
- [ ] Upload progress (a multi-MB body over LAN is not instant — use a `URLSession` delegate or
      an upload task, not a blocking `data(for:)`)
- [ ] The device reboots into the new slot on success; show that and wait for it to come back
- [ ] Failure is reported clearly and states that the device is still on its old firmware —
      dual-slot means a failed flash is not a brick, and the user should know that
- [ ] A confirmation step before flashing
- [ ] Written test-first per the /tdd rule

## Notes

**Do not cross-flash a binary built for a different chip target.** The fleet is multi-target
(see `link-devices` branch `feat/esp-026-kitchensync-multi-target`) and nothing in the current
client checks the binary against the device. That's the one genuine footgun here.

Ideal fix is firmware-side: have `/update` or `/status` expose the chip target so the app can
refuse a mismatch. Until then, at minimum make the confirmation step name the device and require
the user to acknowledge the target — a filename convention is not a safety mechanism, but an
unlabelled "Flash" button is worse.

Left at low priority: it's the least-used path and the most dangerous, so it should land after
the daily-driver screens are solid.
