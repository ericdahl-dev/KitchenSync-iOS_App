## The gap (a real first-run failure)

A user unboxes a device (or one that has never been on their network). It comes up in **setup
mode**, broadcasting its own WiFi AP. The user connects their phone to that AP, opens the
KitchenSync app expecting it to **set the device up** — and the app shows **nothing**.

That is the entire mental model of a companion app for a physical product ("the app sets up
my device"), and today we don't meet it. The app discovers devices **only via Bonjour on the
local network** (`KitchenSyncDiscovery`, `_http._tcp`). A device sitting on its **own** setup
AP is not on the user's LAN yet, so it is invisible, and the user is left to discover — with no
prompting — that they must open a browser to `192.168.4.1` and fill in a web form. Most users
won't. This is the make-or-break first five minutes.

Observed 2026-07-16: a repurposed Super Mini booted as a Touch, couldn't find a known network,
and fell to its `KSTouch-Config` AP. Joined to that AP, the app showed no device and offered no
setup path.

## What the firmware already gives us

Setup is a solved problem on the device side — the app just doesn't use it:

- In AP mode the device broadcasts an **open** setup SSID and serves its normal web server at
  **`192.168.4.1`**:
  - Touch: **`KSTouch-Config`** (`KitchenSyncTouch.ino` → `WiFi.softAP`)
  - P4: **`KitchenSync-Setup`** (`wifi_link.c` `AP_SSID`)
- Provisioning is a **`POST /save`** with `wifi_ssid` / `wifi_pass` (the same form fields the
  firmware HTTP contract already documents); the device stores them and reboots to join.
- `GET /config.json` and `GET /status` answer at `192.168.4.1` too, so the app can confirm it's
  actually talking to one of our devices before it shows a setup screen.

So this is an **app-only** feature — no firmware change. The contract exists.

## Proposed flow

1. **Entry point.** A "Set up a new device" affordance on the empty/discovery screen (and it's
   what the empty state should suggest when no devices are found).
2. **Guide onto the AP** (or join it for the user). Two tiers:
   - *Minimum:* instruct the user to join `KitchenSync-Setup` / `KSTouch-Config` in iOS
     Settings, then return.
   - *Better:* use **`NEHotspotConfiguration`** to join the device AP from within the app (it
     can even scan/prefix-match our setup SSIDs), so the user never leaves the app.
3. **Confirm it's ours.** Probe `http://192.168.4.1/config.json` — if it answers our shape,
   show the device and its model; if not, say "couldn't find a device in setup mode."
4. **Collect the target network + password**, `POST /save` to `192.168.4.1`. Send only the WiFi
   fields (a partial patch — do NOT send `full_form`, which would reset the device's other
   settings to the posted state).
5. **Hand off.** The device reboots and joins; tell the user to reconnect their phone to that
   same network, then **rediscover** the device via Bonjour and drop them on its screen. Close
   the loop so "set up" ends at "here's your working device," not "now go figure out WiFi."

## Considerations / gotchas

- **Local Network permission** already covers reaching `192.168.4.1` (T-011), but the setup AP
  has **no internet**, so iOS flags it "no internet" and may nag; the app must keep using the
  local connection regardless (bind to the AP interface / ignore the captive-network assistant).
- The setup AP is **open** (no password) today — fine for provisioning on the bench, but worth a
  security note: the WiFi password the user types is POSTed over an unencrypted local link. That
  is standard for this class of device and acceptable for setup; flag it, don't over-engineer it.
- **Fleet SSIDs differ per product** (`KitchenSync-Setup`, `KSTouch-Config`). Match on a family
  prefix, not a single string, and keep it in one place (mirror of `DeviceMatch`).
- The **reconnect handoff** is the fiddliest part and the easiest to leave broken — the phone is
  on the device AP (no internet) and must return to the real network before Bonjour can see the
  now-joined device. Design the "reconnect + rediscover" step explicitly; don't leave the user
  on a dead AP wondering if it worked.

## Acceptance criteria

- [ ] From a fresh device on its setup AP, the app presents a first-run setup flow (not an empty
      screen).
- [ ] The app confirms it's a KitchenSync device (via `/config.json` at `192.168.4.1`) before
      offering setup.
- [ ] The user enters their network's SSID + password; the app `POST`s them to `/save`; the
      device joins that network.
- [ ] After the device reboots, the app guides the reconnect and **rediscovers** the device on
      the LAN, ending on its detail screen.
- [ ] Only WiFi fields are sent — provisioning never clobbers the device's other settings.
- [ ] The empty discovery state points the user at "Set up a new device."

## Notes

- No firmware change: this consumes the existing SoftAP + `/save` contract.
- `NEHotspotConfiguration` (join-the-AP-in-app) is the difference between a good and a
  merely-adequate flow, but it needs the Hotspot entitlement — check whether that's worth the
  provisioning profile change, or ship the "join it yourself in Settings" tier first.
- Pairs with the firmware's own "fell to SoftAP" state (the setup banner) — the two ends of the
  same onboarding story. Related: T-025 (dev= TXT identity), T-011 (Local Network permission).
