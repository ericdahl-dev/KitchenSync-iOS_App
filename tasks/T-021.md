## Goal

**"What kind of failure was that?" is a decision this app has been burned by repeatedly — and it is
hand-rolled at four call sites instead of living in one deep module.** The shape "map a thrown
`KitchenSyncClientError.httpStatus(404)` / `DecodingError` / everything-else onto a domain outcome"
appears four times, each producing a slightly different enum:

- `ViewModels/DeviceDetailViewModel.swift:74-93` — `refreshStatus`: decode→`.unsupported`, else→`.unreachable`
- `ViewModels/DeviceDetailViewModel.swift:115-127` — `loadConfig`: 404→`.unsupportedByFirmware`, else→`.failed`
- `ViewModels/DeviceDetailViewModel.swift:159-171` — `apply`: 404→`.unsupportedByFirmware`, status→`.rejectedByDevice`, else→`.unreachable`
- `ViewModels/DeviceListViewModel.swift:123-166` — `refreshAll`: decode→`.undecodable`, else→`.noAnswer`

`DeviceDetailViewModel.StatusAvailability` and `DeviceListViewModel.Reachability` are the **same
three-way concept** — answered-and-read / answered-but-undecodable / didn't-answer — classified
independently in two view models, both deriving it from an identical `catch is DecodingError`.

Two problems: the transport/decode layer's error types (`KitchenSyncClientError`, `DecodingError`)
**leak across the seam** into every view model's `catch`, and the classification itself has **no
locality** — the "undecodable is not gone" rule is written as prose twice.

Deepen: one pure `DeviceFault.classify(Error) -> DeviceFault` module (cases along the lines of
`undecodable` / `notFound` / `rejected(status)` / `unreachable`). Each view model maps that one
fault onto its own presentation enum.

## Acceptance Criteria

- [x] A pure function classifies a thrown request error into a single `DeviceFault` value
- [x] All four call sites above translate a `DeviceFault` into their local enum — none re-inspect
      `KitchenSyncClientError` / `DecodingError` directly
- [x] The classifier is tested **directly at its interface** (feed it errors, assert the fault) —
      no need to drive a whole view model through `StubURLProtocol` to exercise the decision
- [x] The distinct-signals invariant is preserved: undecodable, unreachable and old-firmware stay
      three separate outcomes (T-009, T-010, T-016, T-018 — do not re-collapse them)
- [x] `DeviceListViewModel`'s consecutive-miss counting stays where it is — that is list policy, not
      classification, and only `noAnswer` feeds it
- [x] Existing `DeviceDetailViewModelTests`, `LiveEditFeedbackTests`, `DeviceListViewModelTests`,
      `UnsupportedDeviceTests` all still pass
- [x] Written test-first per the /tdd rule

## Notes

The presentation enums genuinely differ (the list cares reachable/unsupported; the detail-config
path cares unsupportedByFirmware/failed), so the goal is **not** to unify the surface enums — it is
to stop re-deriving the underlying error classification four times. One classifier, four thin
translations.

This is the recurring bug of the codebase in structural form: the same decision, made in more than
one place, drifts. Every one of T-009 / T-010 / T-016 / T-018 was "two situations collapsed into one
signal." Centralising the classification makes the fifth instance harder to write by accident.

Source: architecture review 2026-07-14 (candidate 02). Pairs naturally with T-020 — both are
"a decision spread across call sites, give it one home." Do T-020 first (higher leverage).
