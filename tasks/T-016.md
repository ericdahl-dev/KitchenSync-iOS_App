## Goal

**Found on real hardware, 2026-07-14.** With T-014 landed, the app finally discovers a real
KitchenSync Touch — and then immediately labels it **UNREACHABLE**, while `curl` gets **HTTP 200**
from that same host.

The device is answering perfectly. The app just can't understand what it says.

```
GET http://kstouch-dfd0.local/status   ->  HTTP 200
KsStatus.init(from:)                   ->  THROWS on the first required key, "min"
                                           (11 required keys absent: min, usb, tx, fw,
                                            follow_*, launch, playing, link_owns)
```

`refreshStatus()` does `try? await client.fetchStatus()`, so a **decode** failure and a
**transport** failure collapse into the same `nil`. Three of those and T-010's reachability
counter declares the device gone.

**Telling a user their device is unreachable sends them to debug a network that is working fine.**
The real problem is a protocol mismatch. Same class of bug as T-009 (a `/config.json` 404 is not a
dead network) — this is the identical mistake, one endpoint over.

## Acceptance Criteria

- [ ] A decode failure is distinguished from a transport failure at the client boundary
- [ ] A device that answers but can't be decoded is NOT counted as a reachability miss
- [ ] The list shows something honest for it — e.g. `UNSUPPORTED`, not `UNREACHABLE`
- [ ] The detail screen explains the real cause: this device speaks a different `/status`, its
      firmware needs updating (`link-devices` ESP-029), and points at the OTA path
- [ ] A genuinely absent device still reads `UNREACHABLE` (T-010's behaviour is preserved)
- [ ] A fixture built from the REAL Touch `/status` response is in the test suite
- [ ] Written test-first per the /tdd rule

## Notes

The real device's `/status` (captured 2026-07-14, current `master` firmware — keep this as a
fixture):

```json
{"bpm":0.0,"sync":-1,"peers":0,"clock":1,"transport":0,"cue":0,"tfail":0,"tzero":0,
 "ccancel":0,"drop":0,"burst":0,"gap":1486,"work":93,"over":0,"core":1,
 "wbeats":49,"wclock":1,"wtport":43,"beats":0.00,"locked":0,"bsactive":0,
 "btn":-1,"btnlows":0,"btnpress":0,"clk":"silent","pulses":0}
```

When `link-devices` ESP-029 lands (Touch shares `ks_status.c`), this device will decode and the
state disappears on its own. **That is not a reason to skip this.** The app should never claim a
device is gone when it is sitting there answering — and it should say what's actually wrong, so the
user's next action is "update the firmware", not "check the WiFi".

Note the sequencing gift: the fixture above is a regression test that goes GREEN the day ESP-029
ships. Keep it.
